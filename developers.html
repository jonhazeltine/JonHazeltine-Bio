Under the hood.

I'm a founder, not a career engineer. These products are built on modern TypeScript stacks with heavy AI-assisted development, and I bring developers in as partners — people who want real ownership of real surface area on shipped products. This page is the straight technical story on each one: what it runs on, what the data looks like, and where the work is.

Common Ground

How the portfolio is built

Four products, one philosophy. Everything is TypeScript end-to-end. Everything sits on Supabase (Postgres) as the data layer — three of the four lean hard on PostGIS for geospatial work. Every repo ships through pull requests with a documented architecture (each has its own ARCHITECTURE.md and agent-ready conventions), and AI-assisted development is standard practice here, not an experiment. You'd be joining codebases that are built to be legible — to humans and to agents.

Languages
TypeScript everywhere — strict mode, shared types, Zod validation
Data Layer
Supabase Postgres across all four · PostGIS on three · Drizzle ORM where it fits
Workflow
GitHub PRs, green-build gates, docs-first repos, AI-assisted development as the norm
Hosting
Vercel, Railway, and Expo EAS depending on the product
Project 01 · Live in Production

GrandRapids.RealEstate (Neighborhood Atlas)

A hyperlocal real-estate knowledge graph for West Michigan: 15,000+ boundary polygons (counties down to subdivisions and condos), each enriched with ~140 columns of computed stats — walkability scores, drive times, school ratings, parcel-derived home values — plus live MLS listings geo-matched to every boundary. The largest and most mature codebase in the portfolio.

Frontend
Next.js 16 (App Router, SSG/ISR) · React 18 · Tailwind + shadcn/ui · Mapbox GL JS · Capacitor wrappers for iOS/Android
Backend
Next.js API routes (~250 endpoints) · 25+ scheduled cron jobs · ~400 total routes
Database
Supabase Postgres + PostGIS · 15K boundaries · 690K parcels · 26K amenity POIs · school districts & attendance zones
AI
Anthropic Claude for neighborhood narratives + automated fair-housing compliance scanning · OpenAI embeddings for semantic search
Integrations
MichRIC Spark RESO API (MLS sync every 5 min) · Google Maps & Mapbox geocoding · Resend · Lofty CRM · Google Search Console / IndexNow
Hosting
Vercel (production from main) · Supabase Storage + Transforms as the image CDN
  • Where a partner plugs in: growth features on a stable base, expanding the documented 15-step data-enrichment pipeline to new counties (and eventually new metros), mobile polish, and the SEO/content machinery.
  • Worth knowing: MLS/IDX compliance and fair-housing rules are codified in the repo and enforced in the pipeline — this codebase takes regulatory guardrails seriously.
Project 02 · Live in Production

The Church Map

A national geospatial collaboration platform: 241,000+ churches and 227,000+ Census/TIGER boundaries on an interactive map, with city-scoped community platforms layered on top — prayer journeys, community feeds, church profile claims, and digitally signed partnership agreements. Philanthropic by design.

Frontend
React 18 + Vite · Tailwind + shadcn/ui · Mapbox GL JS v3 · TanStack Query · TipTap rich text
Backend
Express (TypeScript) · ~250 route handlers · Drizzle ORM · 150+ SQL migrations
Database
Supabase Postgres + PostGIS · spatial functions for viewport queries, polygon search, ministry-saturation heatmaps
Data Pipelines
Google Places & OSM church imports · Census/ACS demographics · CDC PLACES health data · Mapbox Uploads API for national tilesets
Services
OpenAI (journey & solutions drafting) · Resend email · AWS S3 · PDF contract generation (pdf-lib + satori)
Hosting
Railway (auto-deploy from GitHub) · Cloudflare CDN/DNS
  • Where a partner plugs in: state-by-state data backfill for the Michigan/Texas/California launch, city-platform onboarding tooling, and performance work on the national map experience.
  • Worth knowing: recent work has been SEO build-out (state and city hub pages, JSON-LD, sitemaps) and the digital contract-signing flow — both shipped and live.
Project 03 · Launching

Be Formed (The Formation App)

A multi-tenant spiritual-formation platform — web app plus native iOS and Android via Capacitor. The interesting architecture is the content model: an immutable template layer (the master journey and achievement blueprints) compiles into module instances, which deploy into per-community live data. One-way flow, enforced with database triggers and audit logging.

Frontend
React 18 + Vite · TypeScript strict · Tailwind + shadcn/ui · TanStack Query · ~14 routes, ~170 components
Mobile
Capacitor 7 → native iOS & Android · Firebase Cloud Messaging push · native Google & Apple Sign-In
Backend
Supabase end-to-end — Postgres, Auth (email/Google/Apple with account auto-linking), Realtime, Edge Functions (incl. automated Apple JWT rotation)
Payments & AI
Stripe community subscriptions (web flow, App Store-compliant) · OpenAI for in-app assistance
  • Where a partner plugs in: mobile release engineering — the launch checklist (transactional email, native OAuth clients, store review) — then post-launch feature velocity.
  • Worth knowing: the feature set is complete and tested; this project is in the last mile between "built" and "in the stores."
Project 04 · In Development

Compass KPI

A KPI-tracking and production-forecasting platform for real estate agents, teams, and coaches. The core domain logic is a forecast engine with strict separation between projected production, leading-indicator activity, and confirmed actuals — modeled with decay and timing rules, never mixed. The earliest-stage venture, and the one with the most greenfield.

App
Expo / React Native + React 19 · TypeScript monorepo · EAS builds & OTA updates · ~19 screens
Backend
Express (TypeScript) · Drizzle ORM · Supabase Postgres · 36+ versioned migrations · ~150 endpoints
Planned Integrations
Stream Chat (team messaging) · Mux (live coaching video) · Stripe subscriptions
Process
Spec-driven: architecture docs, written non-negotiables, sprint gates with per-sprint acceptance test suites
  • Where a partner plugs in: frontend feature sprints, the messaging and live-video integration waves, and launch hardening — the roadmap through launch is written down and gated.
  • Worth knowing: the engine math (forecasting, confidence scoring, deal attribution) already has unit-test coverage; the discipline here is unusually high for a pre-launch product.
Working Together

What partnering looks like

I'm looking for developers who want ownership, not tickets. You'd take real surface area on a product — a pipeline, a platform, a launch — and run it. Collaboration is async and PR-based; every repo carries its own architecture docs and conventions, so you're never reverse-engineering tribal knowledge. Arrangements are flexible by project: contract, revenue share, or equity-style partnership on the right venture. The mission matters here as much as the stack — two of these products are philanthropic, and all of them serve communities I'm personally accountable to.
